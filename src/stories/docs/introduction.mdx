# PMKS+ UI

The one place for how the app's interface looks, behaves and is worded. The components are
rendered live with the app's real stylesheets and Material theme, so a control looks here the way
it looks in the Edit panel; the written rules are the repository's own `docs/*.md`, rendered on
the **Guides** pages at build time so there is exactly one copy of each.

## How it is organized

- **Guides** — the UI style guide (interaction, layout, motion, canvas grammar), the vocabulary
  every label and message is held to, and the code style guide.
- **Tokens** — every color, shadow, radius and gap the app names, read live from the loaded
  stylesheets and grouped by role.
- **Fields** — a number, a pair of numbers, a length-and-angle pair with padlocks, a bare field, a
  color.
- **Choices** — a switch, a pick-one as a segmented pill, a pick-one bound to a form.
- **Actions** — the panel's stroked button, the two-button row, the view-controls button.
- **Structure** — the card, its collapsible sections, its headings, the editable name at the top.
- **Feedback** — the notification kinds, the refusal banners under a panel's title, the right-click
  menu.
- **Reuse backlog** — where the app still hand-rolls one of the above, and which block it should
  use instead.
- **Canvas entities** — planned, not built: joints, links and glyphs arrive with stage S6 of the
  bodies-and-joints migration.

## What it is for

- **Finding the component before building one.** Most "new" controls already exist. Look in the
  section for the job -- a field, a choice, an action -- before writing markup.
- **Seeing every state at once.** Default, disabled with its reason, invalid, and the dense or
  long-label case that breaks a layout. One story per state is the convention, so a state that is
  not here is a state nobody has looked at.
- **Reviewing a change to a component** without having to build a mechanism that happens to show
  it.
- **Reading the rules where the components are.** A refusal's wording, the one breakpoint, one
  undo per gesture: the Guides say it, and the stories beside them show it.

## Build from these, and do not copy a neighbor's CSS

If a panel needs a field, use `input-block`. If it needs a pick-one, use `segmented-block`. If a
block cannot do what you need, **extend the block** and add a story for the new state. Copying the
SCSS of the panel next door gives a control that looks right today and drifts tomorrow; the Reuse
backlog lists the places where that already happened. New colors, radii, shadows and gaps are
tokens, and stylelint refuses a raw hex color anywhere else.

## Running it

- `npm run storybook` starts the gallery at `http://localhost:6006` and reloads it on change.
- `npm run build-storybook` builds a static site into `storybook-static/`, which is gitignored.

## Adding a story

- One file per component: `src/stories/blocks/` for a BLOCKS primitive, `src/stories/shared/`
  for a shared component from elsewhere in `src/app/component/`. Title it `Section/Name`.
- Read the component's inputs from its source. Do not invent inputs, and do not wrap a component
  in one that changes its look. Only `@Input`/`input()` members should appear in the properties
  table; if something else shows up there, it is a public member that should be `protected`.
- A component that injects app services gets a minimal stub from `src/stories/support/stubs.ts`,
  never the real `MechanismService`.
- Use the words on the Vocabulary page. A story is where a label is first read.
