# Gears: Stage 1 and Stage 2 implementation

> **Status:** Reference — computational foundation and solver architecture gate implemented on September 12, 2026. This is the historical Stage 1/2 gate; see [the production V1 report](gears-production.md) for the implemented editing, persistence and lifecycle. [Implementation specification](gears-plan.md).

The architecture gate is supported by the closed four-bar's position, velocity and acceleration
tests, not only by the pair animation. Existing nonlinear and derivative kernels are reused.
Exactly one grounded gear center is the independent input.

## Trying the result

The temporary viewer runs at **http://localhost:4329**. It offers the 20/40 pair, the gear-driven
four-bar, and a 20/100 pair with a five-turn cycle. Play/pause, cycle scrubbing, direction and
speed controls operate on samples generated by the actual Mechanism solver. Speed adjustment
rescales constant-speed time and derivatives; it is not a variable-speed actuator simulation.

With the supported Node version selected:

```text
node scripts/gear-preview.mjs --open
```

This runs the fixture-export test, starts a localhost server, and opens a separate Chrome context.
`--reuse` skips regeneration when `artifacts/gears/samples.json` already exists. Set
`PMKS_GEAR_PORT` to change the port. The browser regression is `node e2e/gear-preview.mjs`;
`PMKS_GEAR_URL` selects a different server. Close the preview process to stop its server.

The viewer is a development artifact, outside the production application. Its circles/ticks
are symbolic; the production gear layer, property panels and Storybook states are covered in [the V1 report](gears-production.md).
The component-gallery contract in the specification still governs that later work.

### 3. Actual model

Gear is a readonly attachment record: id, hostLinkId, centerJointId, referenceJointId, teeth,
module in model units, and optional name. GearMesh carries id, two gear IDs and external kind.
GearAssembly contains both collections. Ratios, periods and headings are derived.
No new Link/Joint subclass, contact pin, independent dependent-shaft input or inertial body exists.

### 4. Ratio compilation

`compileGearDrive(assembly, joints, links)` first validates geometry and the one root input.
It traverses mesh adjacency with reduced bigint numerator/denominator pairs. Revisiting a vertex
requires exact equality; incompatible cycles and unreachable rotors return typed diagnostics.
The complete period is the LCM of every reduced denominator, including idlers.

### 5. Dependent motion entering the solver

The compiled immutable drive retains each host point's authored center-relative offset.
`prescribedGearBodies` rotates all such points by multiplier times q once per candidate.
Remaining points enter the existing coupled solve with those points as moving boundary data.
Velocity is omega cross r; acceleration includes alpha cross r and the centripetal term.
Every host point is included, even if no reduced constraint references it.

### 6. Mobility

Each mesh contributes an angular higher-pair relation. The geometry-based Jacobian and
second-order mobility check include normalized tooth-count coefficients on both body rotations.
Geared mechanisms use that check even if Gruebler's count says one; a redundant even cycle can
remain mobile. The pair and gear-driven four-bar both have one freedom before the input commands
it. Gear-free mechanisms retain their earlier count/rescue and solve routes.

### 7. Continuous q

`Mechanism.gearTravel` stores signed radians from the authored start, parallel to its frames.
The solver carries current q through attempted steps and rollback. A per-mechanism WeakMap
associates snapshot joint arrays with their q for random-order rate queries. Captured drive state
restores the compiled plan, travel/frame lookup, full constraints and coupled route.
`gearMotionAtSample(index)` exposes continuous gear angles and rates; drive profiles use the
stored coordinate instead of unwrapping atan2. Reversing an existing cycle keeps its posed angles
and changes its rates, consistent with existing playback behavior.

### 8. Zero unknowns

The pair still executes the prescribed-body step. Its reduced system has no unknowns, so the
rate path returns analytic boundary rates directly and audits the complete original constraints.
It does not invoke a least-squares system with zero columns or fall back to one-crank rates.

### 9. Closed four-bar

Gear G2 belongs to crank CD. D is prescribed; the existing coupled solver finds E through
the DE/EF length constraints against grounded F. The existing constraint-rate kernel finds its
velocity and acceleration. KinematicsSolver then derives body angular rates through its current
point-rate implementation. No duplicate linkage solver was introduced.

### 10. Full constraint auditing

The emitter collects an additional original-system view with every joint included. Every candidate
geared pose must satisfy its residuals, Jv = 0, and Ja + gamma = 0 before commit. Complete maps
are required; absent moving-point rates cannot quietly become zeros. Prescribed coordinates are
also checked against the compiled gear motion. A real bar joining incompatible prescribed crank
pins is refused and leaves both pose and q unchanged.

### 11. Tests added

The compiler suite has 19 tests and the solver gate has 13. They cover pair/idler/branch ratios,
even/odd cycles, nonzero phase, both directions, acceleration, safe large counts, malformed
definitions, moving centers, module/spacing, one-input enforcement, periods, speed-up sampling,
mobility, full-cycle geometric/derivative closure, finite-difference convergence, rollback,
independent partitions, interleaved rate queries and force refusal.

The preview-export suite adds one opt-in test. During preview generation it checks all exported
frames for six fixture/direction combinations. The browser suite checks playback, scrubbing,
reverse direction, speed scaling, the five-turn endpoint and narrow layout, and records PNG
filmstrip frames under `artifacts/gears/filmstrip/`.

### 13. Pair results

20T at +60 rpm drives 40T at -30 rpm. The output starts at 60 degrees, its reference arm is
length 1, and its pitch radius is 2. The pair produces 721 samples including both endpoints,
q spans 4 pi, and the full cycle is 2 seconds. Shaft angular acceleration is zero at constant
speed; the off-axis point has nonzero centripetal acceleration. Both input directions pass.
The 20/100 pair produces 1,801 samples and a five-second, five-input-turn cycle.

### 14. Four-bar results

The crank-1/coupler-3/rocker-3/ground-4 mechanism produces a complete 721-sample cycle in both
directions with one input and DOF 1. Full-cycle bar-length error stays below 1e-6 model length
(measured maximum approximately 9.84e-7 for the forward fixture). Differentiated bar constraints
and branch continuity pass. Rates agree with the ordinary four-bar formulation at identical
poses to the 1e-8 comparison precision. Centered differences converge under step refinement.

### 15. Differences from the proposal

- Preserve unrounded coupled coordinates on the geared path; existing four-decimal recording
  broke otherwise converged equations. Gear-free recording is unchanged.
- Use tight relative center-spacing validation for unquantized computational geometry. The
  proposed save/load rounding allowance is deferred to that boundary rather than globally applied.
- Round the fastest-gear sample count upward to an integer number of intervals per input turn,
  preserving exact period endpoints without increasing the maximum angular step.
- Use snapshot identity to restore q for current rate APIs, which already receive frame arrays.
- Supply an isolated fixture viewer, not production gear UI or new URL records. Publishing these
  gear fixtures in the URL gallery must wait for the explicitly deferred persistence stage.

### 16. Known limitations

Production MechanismService editing, readiness presentation, URL/share/save, undo/redo,
copy/delete lifecycle, export controls, gear property panels and Storybook stories are not wired
yet. Use the pure partition/Mechanism APIs or the temporary viewer. Arbitrary tooth-count editing
is not available in the viewer; its three mechanisms are tested fixtures.

Only fixed-axis external circular gears on simple hosts are supported. Compounds, moving axes,
internal gears, racks, planetary systems, force transmission and synthesis remain deferred.
Public single-frame force APIs must receive the transmission context; ordinary joint/link arrays
alone do not contain mesh metadata. Model-aware Mechanism and worksheet calls forward it.

The current resource guards are 128 gears, 256 meshes and 6,000 samples. These are conservative
software bounds, not manufacturing limits or a performance guarantee for every linkage topology.
The fixture gate proves the pair and closed four-bar; it is not a claim that every existing
linkage combined with arbitrary gears has been validated.

### 17. Major solver rewrite

The original conclusion holds for this scope. Exact gear motion fits the existing moving-boundary
position and derivative kernels. The additions are domain compilation, higher-pair mobility,
orchestration, auditing and state/sampling; the nonlinear solver itself was not replaced.
